 #39 PROMETHEUS + GRAFANA MONITORING
  - /metrics (Prometheus format) on every service: request-service, matching-service, coordinator, 6 storage nodes
      every service : HTTP requests by route template / method / status + latency histogram
      request-svc   : requests created (by type), published to RabbitMQ (ok / failed / broker down),
                      status changes, resources registered
      matching-svc  : matches by outcome (matched / no_match / skipped) and path (queue / api),
                      TIME FROM REQUEST TO MATCH (histogram), messages consumed, retries, gave up,
                      in-flight messages, reconciler fixes, sweeper re-queues, broker connected
      coordinator   : NODE UP/DOWN per node, node status, ready replicas per shard, SHARD HEALTH,
                      records per node, heartbeat age, reads / writes, READ FAILOVERS,
                      node-down events, degraded writes (live view exported at scrape time = always exact)
      storage node  : RESYNC DURATION (histogram + last), resyncs ok/failed, records received / applied,
                      local records, ready flag
  - RabbitMQ's built-in rabbitmq_prometheus plugin scraped: QUEUE DEPTH (waiting / unacked), consumers, retry queue
  - Prometheus v3.15.1, scraping every 5 s
      Compose    : static targets + DNS discovery (finds every replica of request / matching service)
      Kubernetes : pod discovery via the Kubernetes API (read-only Role), so pods added by scaling or
                   recovery are scraped within seconds; NodePort 30090
  - Grafana 13.2.5 with the Prometheus datasource and the "ERMS overview" dashboard provisioned at start-up
      21 panels in 4 sections (cluster health / messaging + autoscaling / latency + API / failures + recovery),
      refresh 5 s, home page of Grafana; viewing needs no login (read-only), admin password random
      (.env on Compose, Secret grafana-credentials on Kubernetes); NodePort 30030
  - Dashboard generated from monitoring/grafana/build_dashboard.py (easy to change)

 #18 KEDA AUTOSCALING ON RABBITMQ QUEUE DEPTH
  - KEDA v2.21.0 installed by k8s/deploy.sh (skipped with a warning when offline / SKIP_KEDA=1)
  - ScaledObject: matching-service between 2 and 6 pods, 1 pod per 5 messages waiting in matching.requests,
    checked every 5 s; scale up immediately, scale down 30 s after the queue drained (default would be 5 min)
  - KEDA's broker login from Secret keda-rabbitmq via a TriggerAuthentication (no password in any manifest)
  - scripts/matching-replicas.sh N|auto: pin the replica count (KEDA paused-replicas) / back to automatic,
    because with KEDA a plain `kubectl scale` is undone by its HPA within seconds (tested)
  - scripts/keda-demo.sh: 200-request burst with a live table of queue depth / ready pods / desired pods
  - old CPU-based HPA removed (two autoscalers on one Deployment fight each other)

 FOUND AND FIXED WHILE TESTING
  - Timestamps could run backwards when WSL / NTP stepped the system clock back (seen once: updated_at earlier
    than created_at). now_iso() is now monotonic per process; unit test added.
  - "Failovers rise" was promised for the demo but not yet verified: a read that switched to another replica
    during a prefix SCAN was not counted as a failover. All read paths now count it; unit test + live test
    (kill the replica that serves the reads -> failover counter rises on the dashboard) added.
  - RabbitMQ had no restart policy in docker-compose.yml (every other service had one). When the WSL machine
    rebooted during the final checks, all containers came back except RabbitMQ, so Compose had no broker.
    Added `restart: unless-stopped`; tested by killing RabbitMQ from inside: Docker restarted it in 2 s and
    the services reconnected by themselves. (Kubernetes was not affected: StatefulSets always restart pods;
    after the same reboot all 14 erms pods, the 3 KEDA pods and the ScaledObject came back on their own.)
