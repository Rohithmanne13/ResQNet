 PART 2 - THE 5 OPERATIONS                                                          (PDF §1, §3, §5)

 TEST 2.1  registerResource(type, location, availability)  -> POST /resources
 DO      $ call POST /resources '{"type":"water","kind":"ngo","name":"NGO water tanker","availability":2,"location":'"$(loc 1)"'}'
         $ RES=$(last_id); echo $RES
 EXPECT  HTTP 201; id "res-water-<hex>", status "available", availability 2, kind "ngo".
 WHY     201 Created = a new record was stored. Status starts "available" because it has free units. The type is
         part of the id so matching can scan only resources of that type (fast).

 TEST 2.2  A volunteer can be registered too
 DO      $ call POST /resources '{"type":"transportation","kind":"volunteer","name":"Volunteer boat","availability":1,"location":'"$(loc 2)"'}'
 EXPECT  HTTP 201, kind "volunteer".
 WHY     PDF §3.2: resources include volunteers, NGOs and other providers (kinds: resource, volunteer, ngo, other).

 TEST 2.3  createRequest(type, location, details)  -> POST /requests
 DO      $ call POST /requests '{"type":"water","details":"Family of 4 needs drinking water","priority":"high","auto_match":false,"location":'"$(loc 0)"'}'
         $ REQ=$(last_id); echo $REQ
 EXPECT  HTTP 201; id "req-<hex>", type, location, details, status "pending", created_at (creation time),
         history [pending], "_storage": shard 0/1/2, replicas = the 2
         nodes of that shard, "degraded": false.
 WHY     A new request always starts "pending" (not yet helped). degraded false = BOTH replicas confirmed the write.
         (auto_match false only so that YOU can match it by hand in 2.5; normally it is matched automatically.)

 TEST 2.4  getRequest(requestId)  -> GET /requests/{id}
 DO      $ call GET /requests/$REQ
 EXPECT  HTTP 200, exactly the data from 2.3, plus "_storage": "served_by": one node of its shard.
 WHY     The coordinator computes the shard from the id and reads from a ready replica of THAT shard.

 TEST 2.5  matchRequest(requestId)  -> POST /match/{id}
 DO      $ call POST /match/$REQ
         $ call GET /resources/$RES
 EXPECT  HTTP 200, "result": "matched", the NGO water tanker, "distance_km" ~1.0.  The resource now has
         availability 1 and lists the request in assigned_requests.
 WHY     Same type (water), available, within 50 km, nearest first. Every assignment takes one unit (2 -> 1).

 TEST 2.6  Matching is idempotent
 DO      $ call POST /match/$REQ
 EXPECT  HTTP 200, "result": "skipped" (already matched); the tanker still has availability 1.
 WHY     A request must never take a second unit (repeated calls or redelivered RabbitMQ messages are harmless).

 TEST 2.7  updateStatus(requestId, status)  -> PUT /requests/{id}/status
 DO      $ call PUT /requests/$REQ/status '{"status":"in_progress","note":"tanker on the way"}'
         $ call PUT /requests/$REQ/status '{"status":"resolved"}'
         $ call GET /resources/$RES
         $ call GET /requests/$REQ
 EXPECT  HTTP 200 both times; the tanker is back to availability 2; history = pending -> matched -> in_progress
         -> resolved (each with a time).
 WHY     Life cycle pending -> matched -> in_progress -> resolved. Resolving frees the unit for the next request.

 TEST 2.8  Resource availability updates  -> PUT /resources/{id}/status
 DO      $ call PUT /resources/$RES/status '{"availability":0}'
         $ call PUT /resources/$RES/status '{"availability":3,"status":"available"}'
         $ call PUT /resources/$RES/status '{"status":"offline"}'
 EXPECT  200 each time: availability 0 -> status "busy" automatically; 3 -> "available"; then "offline".
 WHY     Status follows capacity: 0 free units = busy. Offline = taken out of service (never matched, see 4.4).

 TEST 2.9  Lists, filters, paging, summary
 DO      $ call GET "/resources?type=transportation&status=available&limit=3"
         $ call GET "/requests?status=resolved&order=desc&limit=2"
         $ call GET /summary
 EXPECT  200; only items matching the filters, newest first, "count" = returned, "total" = all matches.
         /summary: request counts by status and type, resources by status / type / kind, free units.
 WHY     A list is a scatter-gather over all 3 shards (the coordinator asks one replica of each and merges).

 TEST 2.10 Cancel and re-open
 DO      $ call POST /requests '{"type":"water","details":"re-open test","auto_match":false,"location":'"$(loc 0)"'}'; R2=$(last_id)
         $ call PUT /resources/$RES/status '{"availability":1,"status":"available"}'
         $ call POST /match/$R2
         $ call PUT /requests/$R2/status '{"status":"pending"}'        # re-open
         $ call GET /resources/$RES
         $ call PUT /requests/$R2/status '{"status":"cancelled"}'
 EXPECT  matched (tanker 1 -> 0, busy) -> re-opened to "pending" (tanker back to 1, available) -> "cancelled".
 WHY     Re-opening or cancelling gives the unit back, so capacity is never lost.

 PART 4 - MATCHING RULES                                                                       (PDF §7)
=====================================================================================================================
$ newplace

 TEST 4.1  Nearest wins (type + location)
 DO      $ call POST /resources '{"type":"water","name":"Tanker NEAR","availability":2,"location":'"$(loc 2)"'}'; NEAR=$(last_id)
         $ call POST /resources '{"type":"water","name":"Tanker FAR","availability":5,"location":'"$(loc 10)"'}'
         $ call POST /resources '{"type":"food","name":"Food truck (closest, wrong type)","availability":5,"location":'"$(loc 0)"'}'
         $ call POST /requests '{"type":"water","details":"rule test","auto_match":false,"location":'"$(loc 0)"'}'; Q=$(last_id)
         $ call POST /match/$Q
 EXPECT  matched to "Tanker NEAR", distance_km ~2.0.
 WHY     Only the same TYPE counts (the food truck at 0 km is ignored); among those the NEAREST wins, even though
         the far tanker has more units (capacity is only the tie-breaker). Distance = haversine (earth curvature).

 TEST 4.2  50 km limit
 DO      $ newplace
         $ call POST /resources '{"type":"rescue","name":"Boat 60 km","availability":1,"location":'"$(loc 60)"'}'
         $ call POST /requests '{"type":"rescue","details":"limit test","auto_match":false,"location":'"$(loc 0)"'}'; Q=$(last_id)
         $ call POST /match/$Q
         $ call POST /resources '{"type":"rescue","name":"Boat 40 km","availability":1,"location":'"$(loc 40)"'}'
         $ call POST /match/$Q
 EXPECT  first 409 "no suitable available resource"; after adding the 40 km boat: 200, matched, distance_km ~40.
 WHY     MAX_MATCH_DISTANCE_KM = 50: help that is too far away is not useful, so it is not assigned.

 TEST 4.3  Capacity: a resource is never over-assigned
 DO      $ newplace
         $ call POST /resources '{"type":"shelter","name":"Shelter (1 bed)","availability":1,"location":'"$(loc 1)"'}'; S=$(last_id)
         $ call POST /requests '{"type":"shelter","auto_match":false,"location":'"$(loc 0)"'}'; A=$(last_id)
         $ call POST /requests '{"type":"shelter","auto_match":false,"location":'"$(loc 0)"'}'; B=$(last_id)
         $ call POST /match/$A
         $ call POST /match/$B
         $ call GET /resources/$S
 EXPECT  A: 200 matched.  B: 409 (no suitable resource).  Shelter: availability 0, status "busy".
 WHY     One unit, one assignment. The unit is claimed with compare-and-set, so it can never be given twice.

 TEST 4.4  Offline and busy resources are never matched
 DO      $ call PUT /requests/$A/status '{"status":"resolved"}'        # frees the bed
         $ call PUT /resources/$S/status '{"status":"offline"}'
         $ call POST /match/$B
         $ call PUT /resources/$S/status '{"status":"available"}'
         $ call POST /match/$B
 EXPECT  409 while offline; 200 matched after it is available again.
 WHY     Only status "available" with free units is a candidate.

 PART 5 - ASYNCHRONOUS PROCESSING WITH RABBITMQ                                           (PDF §6, §7)
=====================================================================================================================
$ newplace
$ call POST /resources '{"type":"water","name":"Async tanker","availability":100,"location":'"$(loc 1)"'}'; T=$(last_id)

 TEST 5.1  The flood scenario: request -> RabbitMQ -> matching worker -> storage                   (PDF §1.1)
 DO      $ call POST /requests '{"type":"water","details":"flood victim","location":'"$(loc 0)"'}'; Q=$(last_id)
         $ sleep 2; call GET /requests/$Q
 EXPECT  The POST answers at once with 201, "status": "pending", "queued": true. 2 s later: "matched" to the
         Async tanker; the history shows "pending" by a request-service pod, then "matched" by a matching-service
         pod (the worker that took the message from RabbitMQ).
 WHY     The API only stores the request and publishes a message; it does not wait for matching. A matching
         worker consumes the message, matches and updates storage. This is the asynchronous flow of PDF §7
         (the client gets a fast answer even if matching takes time).

 TEST 5.2  Many requests are shared by the workers (competing consumers)
 DO      $ BURST=$(for i in $(seq 1 40); do curl -s -X POST $API/requests -H 'Content-Type: application/json' -d '{"type":"water","details":"burst","location":'"$(loc 0)"'}' | python3 -c 'import json,sys; print(json.load(sys.stdin)["id"])' & done; wait)
         $ for i in 1 2 3 4 5; do queue; sleep 2; done
         $ for id in $BURST; do curl -s $API/requests/$id | python3 scripts/show.py worker; done | sort | uniq -c
 EXPECT  All 40 accepted. The queue shows messages waiting / being processed, then 0. All 40 "matched",
         split between BOTH matching pods.
 WHY     Both pods consume from the same durable queue; RabbitMQ hands each message to one consumer only
         (prefetch 2), so work is load-balanced and nothing is processed twice.

 TEST 5.3  Exchange -> queue topology
 DO      $ curl -s -u erms:$RPASS $RABBIT/api/exchanges/%2F/erms.requests/bindings/source | python3 -m json.tool | grep -E '"(destination|routing_key)"'
 EXPECT  erms.requests -> matching.requests with routing key "request.#".
 WHY     Topic exchange: the API publishes "request.<type>"; the queue receives all of them.

 TEST 5.4  Matching service down -> messages wait in RabbitMQ (nothing is lost)
 DO      $ ./scripts/matching-replicas.sh 0                  # Compose: docker compose stop matching-service
         $ call POST /requests '{"type":"water","details":"while matching is down","location":'"$(loc 0)"'}'; Q=$(last_id)
         $ queue
         $ call POST /match/$Q
         $ ./scripts/matching-replicas.sh auto               # Compose: docker compose start matching-service
         $ sleep 20; call GET /requests/$Q
 EXPECT  201 (accepted). queue: 1 message waiting, 0 consumers. /match: 503 (matching service unavailable).
         After the restart: the request is "matched".
 WHY     The queue is durable and the message persistent: it waits until a consumer is back. 503 = a needed
         service is down (not the client's fault). This is fault tolerance through asynchronous messaging.

 TEST 5.5  RabbitMQ itself down -> the request is still accepted and matched later
 DO      $ kubectl -n erms scale sts rabbitmq --replicas=0       # Compose: docker compose stop rabbitmq
         $ sleep 10; call GET /health
         $ call POST /requests '{"type":"water","details":"while RabbitMQ is down","location":'"$(loc 0)"'}'; Q=$(last_id)
         $ kubectl -n erms scale sts rabbitmq --replicas=1       # Compose: docker compose start rabbitmq
         $ sleep 75; call GET /requests/$Q
 EXPECT  /health: "broker_connected": false. POST: 201 with "queued": false. About a minute after RabbitMQ is
         back: "matched" (history note from the sweeper).
 WHY     The request is stored FIRST, so it is never lost. The sweeper in the matching service re-queues requests
         that stayed "pending" longer than STALE_PENDING_SECONDS (30 s) once the broker is back.

 TEST 5.6  Retries, "unmatched", and automatic revival
 DO      $ newplace
         $ call POST /requests '{"type":"medicine","details":"nothing nearby yet","location":'"$(loc 0)"'}'; Q=$(last_id)
         $ sleep 75; call GET /requests/$Q | grep -E '"status"|match_attempts' | head -3
         $ call POST /resources '{"type":"medicine","name":"Pharmacy van","availability":1,"location":'"$(loc 3)"'}'
         $ sleep 30; call GET /requests/$Q | grep -E '"status"|"name"' | head -3
 EXPECT  After ~1 minute: "unmatched", match_attempts 12. Within ~30 s of the pharmacy van appearing: "matched".
 WHY     A failed attempt goes to the retry queue (5 s delay, without blocking a worker); after 12 attempts the
         request is "unmatched" instead of retrying forever. The sweeper revives "unmatched" requests as soon as a
         suitable resource exists, so nobody is forgotten.

 TEST 5.7  Matching worker statistics
 DO      $ kubectl -n erms exec deploy/matching-service -- python -c "import urllib.request; print(urllib.request.urlopen('http://localhost:8000/stats').read().decode())"
                                         # Compose: docker compose exec matching-service python -c "...same..."
 EXPECT  {"worker": "<pod name>", "broker_connected": true, "counters": {...}} - the counters (messages consumed,
         matched, retried, swept ...) grow as that pod processes work; {} right after the pod started.
 WHY     Each worker reports what IT did, so you can see that the work is really shared between pods.

 TEST 5.8  RabbitMQ management UI
 DO      Open http://localhost:30672 (Compose: http://localhost:15672). User: erms, password:
         $ ./scripts/rabbit-password.sh                      # Compose: COMPOSE=1 ./scripts/rabbit-password.sh
         Go to Queues -> matching.requests, then run TEST 5.2 again.
 EXPECT  Exchanges erms.requests + erms.retry; queues matching.requests (2 consumers) + matching.retry. The
         "Queued messages" chart rises and falls back to 0 during the burst. Login "guest" is refused.
 WHY     This is the broker's own view of the asynchronous messaging. The retry queue holds failed attempts for
         5 s and then sends them back to erms.requests (delayed retry without blocking a worker).

 PART 6 - MULTIPLE SIMULTANEOUS REQUESTS                                                       (PDF §11)
=====================================================================================================================

 TEST 6.1  30 simultaneous matches against 20 units
 DO      $ newplace
         $ call POST /resources '{"type":"food","name":"Food bank (20 units)","availability":20,"location":'"$(loc 1)"'}'; FB=$(last_id)
         $ IDS=$(for i in $(seq 1 30); do curl -s -X POST $API/requests -H 'Content-Type: application/json' -d '{"type":"food","auto_match":false,"location":'"$(loc 0)"'}' | python3 -c 'import json,sys; print(json.load(sys.stdin)["id"])' & done; wait)
         $ echo $IDS | wc -w
         $ (for id in $IDS; do curl -s -o /dev/null -w '%{http_code}\n' -X POST $API/match/$id & done; wait) | sort | uniq -c
         $ call GET /resources/$FB | grep -E '"availability"|"status"'
 EXPECT  30 distinct ids (created at the same moment). Exactly "20 200" and "10 409". Food bank: availability 0,
         status "busy".
 WHY     30 parallel matchers compete for 20 units. Each unit is claimed with compare-and-set (write only if the
         version is unchanged); a loser re-reads and retries. So exactly 20 succeed and the rest are correctly
         refused: never over-assigned, never a unit lost.

 PART 7 - SHARDING AND DATA DISTRIBUTION                                                        (PDF §4)
=====================================================================================================================

 TEST 7.1  Requests spread over all 3 shards
 DO      $ for id in $BURST; do curl -s $API/requests/$id | python3 -c 'import json,sys; print("shard", json.load(sys.stdin)["_storage"]["shard"])'; done | sort | uniq -c
         $ cluster
 EXPECT  All 3 shards used, roughly a third each; cluster: similar key counts on the 3 shards.
 WHY     Ids are random, and the hash spreads random keys evenly.

 TEST 7.2  The shard is sha256(key) mod 3, chosen by the coordinator (not the client)
 DO      $ ccall GET /internal/shard-of/request:$REQ
         $ python3 -c "import hashlib,sys; k='request:'+sys.argv[1]; print(k, '-> sha256 mod 3 =', int.from_bytes(hashlib.sha256(k.encode()).digest()[:8],'big') % 3)" $REQ
         $ call GET /requests/$REQ | grep -A1 '"shard"'
 EXPECT  The same shard number three times.
 WHY     A stable hash means every service computes the same shard for a key. The client only ever talks to the
         API; it never knows or chooses where data lives (PDF §4: storage is transparent to clients).

 PART 8 - COORDINATOR <-> STORAGE INTERNAL API                                                  (PDF §6)
=====================================================================================================================

 TEST 8.1  Registration and heartbeats
 DO      $ ccall GET /internal/nodes | grep -E '"node_id"|"status"|"heartbeat_age_s"'
         $ ccall POST /internal/nodes/heartbeat '{"node_id":"nobody","shard_id":0,"url":"http://x"}'
 EXPECT  6 nodes, all "ready", heartbeat age under ~2 s. Unknown node: 404 ("register first").
 WHY     Each storage node registers at start, then sends a heartbeat every 2 s. A heartbeat from a node that never
         registered is refused.

 TEST 8.2  Store / retrieve / delete
 DO      $ ccall PUT /internal/data/demo:hello '{"value":{"msg":"hi"}}'
         $ ccall GET /internal/data/demo:hello
         $ ccall DELETE /internal/data/demo:hello
         $ ccall GET /internal/data/demo:hello
 EXPECT  200 (version, acked by 2 nodes) -> 200 {"msg":"hi"} -> 200 -> 404.
 WHY     The coordinator routes each key to its shard and writes to both replicas. Delete leaves a "tombstone"
         so a node that was down also learns about the delete when it resyncs.

 TEST 8.3  Compare-and-set (the basis of safe concurrent matching)
 DO      $ ccall PUT "/internal/data/demo:cas?if_version=0" '{"value":{"n":1}}'
         $ ccall PUT "/internal/data/demo:cas?if_version=0" '{"value":{"n":2}}'
         $ ccall DELETE /internal/data/demo:cas
 EXPECT  first 200; second 409 "version conflict" with the current version.
 WHY     if_version=0 means "only if it does not exist yet". The second writer is told it lost, instead of
         silently overwriting. Matching uses this on every claim (PART 6).

 PART 9 - STORAGE-NODE FAILURE, REPLICAS, RECOVERY                                              (PDF §8)
=====================================================================================================================

 TEST 9.1  BEFORE: a record on shard 1
 DO      $ for i in $(seq 1 30); do call POST /requests '{"type":"food","details":"written BEFORE the failure","auto_match":false,"location":{"lat":9.93,"lon":76.26}}' >/dev/null; [ "$(field 'd["_storage"]["shard"]')" = 1 ] && break; done; K1=$(last_id); echo "$K1 is on shard 1"
         $ call GET /requests/$K1 | grep served_by
 EXPECT  served_by storage-shard-1-0                    (Compose: storage-1a)

 TEST 9.2  DURING: stop one replica -> detected, data still available
 DO      $ kubectl -n erms scale sts/storage-shard-1 --replicas=1      # stops storage-shard-1-1
                                                                       # Compose: docker compose stop storage-1b
         $ sleep 10; cluster
         $ call GET /requests/$K1 | grep served_by
 EXPECT  cluster: storage-shard-1-1 "down"; shard 1 still healthy. The read: 200, from storage-shard-1-0.
 WHY     No heartbeat for 6 s -> the coordinator marks the node down and stops routing to it (detect + avoid).
         The other replica has a full copy, so reads continue without error (PDF §8: replica keeps serving).

 TEST 9.3  DURING: writes, matching and status updates continue
 DO      $ for i in $(seq 1 30); do call POST /requests '{"type":"food","details":"written DURING the failure","auto_match":false,"location":{"lat":9.93,"lon":76.26}}' >/dev/null; [ "$(field 'd["_storage"]["shard"]')" = 1 ] && break; done; K2=$(last_id); field 'd["_storage"]'
         $ call PUT /requests/$K1/status '{"status":"cancelled"}' | head -1
 EXPECT  201 with "degraded": true (only 1 of 2 copies acknowledged); the status update: 200.
 WHY     Availability first: one live copy is enough to accept writes. "degraded" honestly reports that the second
         copy is missing - it is filled in when the node comes back.

 TEST 9.4  AFTER: restart -> resync -> ready again
 DO      $ kubectl -n erms scale sts/storage-shard-1 --replicas=2      # Compose: docker compose start storage-1b
         $ kubectl -n erms rollout status sts/storage-shard-1; sleep 5
         $ cluster
         $ kubectl -n erms logs storage-shard-1-1 | grep "SYNC complete" | tail -1
 EXPECT  storage-shard-1-1 "ready", SAME key count as storage-shard-1-0. Log: "SYNC complete ... applied N
         updates" (N >= 1: the writes it missed, incl. K2 and the cancel of K1).
 WHY     A returning node first copies a snapshot from its ready partner and merges it by version (newest wins),
         and only then serves reads - so it never answers with stale data (PDF §8: recovery + synchronization).

 TEST 9.5  Kill the replica that SERVES the reads (failover)
 DO      $ kubectl -n erms delete pod storage-shard-1-0
         $ call GET /requests/$K1 | grep served_by
         $ kubectl -n erms wait --for=condition=Ready pod/storage-shard-1-0 --timeout=120s; sleep 5; cluster
 EXPECT  The read still answers 200, now served_by storage-shard-1-1. The pod comes back with the same name and
         disk, resyncs, and is "ready" again.
 WHY     Reads go to the first ready replica and fail over to the next one; the StatefulSet recreates the pod
         with its persistent volume, so only the missed updates are copied.

 TEST 9.6  Coordinator down -> clean error; coordinator back -> cluster rebuilt by itself
 DO      $ kubectl -n erms scale deploy/coordinator --replicas=0
         $ sleep 10; call GET /requests/$K1
         $ kubectl -n erms scale deploy/coordinator --replicas=1
         $ sleep 20; cluster; call GET /requests/$K1 | head -1
 EXPECT  While down: 503 "storage coordinator unreachable" (and /health of the API still 200). After ~10 s: all
         6 nodes registered again, all ready, the read 200.
 WHY     503 = a dependency is down, reported clearly instead of crashing. The coordinator keeps no data itself:
         nodes re-register via their heartbeat loop, replicas of a shard merge each other's data before serving.

 PART 14 - PROTECTIONS AGAINST RARE FAILURES (proven by automated tests)
=====================================================================================================================
 These protect against failures that are hard to cause by hand (a crash at one exact moment), so each one is
 proven by an automated test that forces that exact situation. Run one with the command shown; EXPECT "1 passed".
 [U] = unit test:        .venv/bin/python -m pytest -v tests/unit -k NAME            (no cluster needed)
 [K] = Kubernetes test:  .venv/bin/python -m pytest -v -s tests/k8s -k NAME          (after the export line in PART 15)
 [I] = integration test: .venv/bin/python -m pytest -v tests/integration -k NAME     (on Compose; on Kubernetes add
                         the variables from RUN_AND_TEST_GUIDE.txt PART 8)

 14.1  Capacity leak repaired (the "reconciler")                [I] test_capacity_leak_is_reconciled
                                                               [I] test_lost_claim_is_reconciled
 EXPECT  A unit left claimed by a crashed matcher is given back; a request that lost its claim is re-opened and
         matched again.
 WHY     A matcher can crash between "take a unit" and "mark the request matched". The reconciler in every
         matching pod finds such leftovers after a grace period (60 s) and repairs them with compare-and-set.

 14.2  A returning stale replica is never trusted alone         [I] test_coordinator_restart_never_serves_a_stale_replica
                                                               [K] test_coordinator_restart_rebuilds_the_cluster_safely
                                                               [U] test_first_returning_replica_is_not_trusted_alone
 EXPECT  After a coordinator restart, a replica that may have missed writes is "waiting" (never serves reads) until
         its partner is back or 8 s pass; then both merge each other's data, newest version wins.
 WHY     Without a ready partner there is nobody to check its data against; serving it could return old values.

 14.3  A lost sync order is re-sent (found and fixed on 2026-11-20)   [U] test_lost_sync_order_is_resent_instead_of_deadlocking
                                                               [U] test_node_is_never_ready_without_completing_its_sync
 EXPECT  If the heartbeat reply carrying "copy your partner's data now" is lost, the next heartbeat sends it again;
         a node only counts as ready after it reports that exact sync (sync_id) as done.
 WHY     Otherwise a node could stay out of service forever, or be trusted without the writes it missed.

 14.4  Write accepted with one copy survives losing both pods    [K] test_degraded_write_survives_losing_both_pods_of_a_shard
 EXPECT  A "degraded" write (one copy) is still there after BOTH pods of the shard are deleted and come back.
 WHY     Every write is flushed to disk on a persistent volume before it is acknowledged.

 14.5  Versions never go backwards                              [U] test_versions_never_go_backwards_after_coordinator_restart
 EXPECT  After a coordinator restart, new versions are higher than every version already stored.
 WHY     Newest-version-wins would otherwise silently drop new writes (e.g. after a clock jump).

 14.6  Redelivered message = no second unit                     [U] test_try_assign_is_idempotent_per_request
                                                               [U] test_matcher_reuses_a_claim_it_already_holds
 EXPECT  Processing the same request twice keeps exactly one unit.
 WHY     RabbitMQ re-delivers a message if a worker crashes before acknowledging it (at-least-once delivery).

 14.7  Scale-down loses nothing (graceful drain)                [K] test_scale_matching_service_to_4
 EXPECT  4 -> 2 matching pods while work is running: every request matched, capacity exact, API always answering.
 WHY     A stopping matching pod stops taking messages and finishes the ones it holds before exiting.

 14.8  Queued messages survive a broker restart                 [I] test_queued_requests_survive_broker_restart_and_match_503_when_matching_down
                                                               [I] test_broker_outage_requests_are_not_lost
 EXPECT  Messages waiting in RabbitMQ are still there after it restarts and are then matched.
 WHY     Durable queue + persistent messages + RabbitMQ data on a persistent volume.

 14.9  RabbitMQ password from a Secret                          [K] test_rabbitmq_credentials_come_from_a_secret
 EXPECT  Pods get the password via secretKeyRef; the default guest:guest login is rejected.
