 §7  REQUEST PROCESSING
=====================================================================================================================
 PDF  "When an emergency request requiring a resource match is created, the system should process it
       asynchronously" - steps 1 to 6, matching on at least resource type and location.

 We make the 6 steps VISIBLE by pausing the Matching Service, so the message is seen waiting in RabbitMQ.

 PREPARE: a resource to match against
 $ call POST /resources '{"type":"water","kind":"ngo","name":"NGO water tanker","availability":3,"location":'"$(loc 2)"'}'
 $ T=$(last_id)
 $ ./scripts/matching-replicas.sh 0            # pause the Matching Service (0 pods)
                                               # Compose: docker compose stop matching-service

 ---- STEP 1  "The client submits an emergency request."
 DO      $ call POST /requests '{"type":"water","details":"Flood victim needs drinking water","priority":"high","location":'"$(loc 0)"'}'
         $ Q=$(last_id)
 EXPECT  HTTP 201 immediately, "status": "pending", "queued": true.
 WHY     The client (terminal / web UI) sends one HTTP call to the Request Service and gets an answer at once -
         it does NOT wait for matching. That is what "asynchronous" means.

 ---- STEP 2  "The Request Service stores the request."
 DO      $ call GET /requests/$Q
 EXPECT  HTTP 200, the same request; "_storage": "shard": 0/1/2, "served_by": a storage node of that shard.
 WHY     The request was written to distributed storage (both replicas of its shard) BEFORE it was published,
         so it can never be lost - even if RabbitMQ were down.

 ---- STEP 3  "The request is published to RabbitMQ."
 DO      $ queue
         $ prom 'sum(erms_requests_published_total{result="ok"})'
 EXPECT  queue matching.requests  ready=1  unacked=0  consumers=0   (the message is waiting)
         the published counter went up by 1.
 WHY     The Request Service published a "request.created" message to exchange erms.requests; it is routed to
         the durable queue matching.requests. Nobody consumes it right now, so it waits there safely.

 ---- STEP 4  "The Matching Service consumes the message."
 DO      $ ./scripts/matching-replicas.sh auto          # Compose: docker compose start matching-service
         $ sleep 20
         $ queue
 EXPECT  queue matching.requests  ready=0  unacked=0  consumers=2
 WHY     The 2 matching pods subscribe to the queue again and one of them takes the waiting message (ready
         1 -> 0). It acknowledges the message only after the work is done, so a crash would re-deliver it.

 ---- STEP 5  "A suitable available resource is identified."
 ---- STEP 6  "The resource is assigned and the corresponding statuses are updated."
 DO      $ call GET /requests/$Q
         $ call GET /resources/$T
 EXPECT  request:  "status": "matched", "assigned_resource": res-water-..., "assignment": resource_name
                   "NGO water tanker", "distance_km": ~2.0, "matched_by": matching-service-<pod>, "via": "queue";
                   history: pending (by request-service-<pod>) -> matched (by matching-service-<pod>)
         resource: "availability" 3 -> 2, the request listed in assigned_requests
 WHY     Step 5: the worker searched resources of the same TYPE that are available, have free units and are
         within 50 km, and picked the NEAREST. Step 6: it took one unit of the resource (claimed safely with
         compare-and-set) and set the request to "matched" - BOTH records updated in storage. "via": "queue"
         proves it was the RabbitMQ path.
 AUTO    test_flood_victim_needs_drinking_water_end_to_end

 ---- MATCHING CONSIDERS RESOURCE TYPE AND LOCATION
 DO      $ newplace
         $ call POST /resources '{"type":"water","name":"Tanker NEAR","availability":2,"location":'"$(loc 2)"'}'
         $ call POST /resources '{"type":"water","name":"Tanker FAR","availability":5,"location":'"$(loc 10)"'}'
         $ call POST /resources '{"type":"food","name":"Food truck (closest, wrong type)","availability":5,"location":'"$(loc 0)"'}'
         $ call POST /requests '{"type":"water","details":"type + location test","auto_match":false,"location":'"$(loc 0)"'}'
         $ call POST /match/$(last_id)
 EXPECT  HTTP 200, matched to "Tanker NEAR", distance_km ~2.0.
 WHY     TYPE: the food truck at 0 km is ignored (wrong type). LOCATION: of the two water tankers the nearer one
         wins, even though the far one has more units. Distance = haversine (great-circle) distance.
 DO      $ newplace
         $ call POST /resources '{"type":"rescue","name":"Boat 60 km","availability":1,"location":'"$(loc 60)"'}'
         $ call POST /requests '{"type":"rescue","details":"distance limit","auto_match":false,"location":'"$(loc 0)"'}'
         $ RQ=$(last_id); call POST /match/$RQ
         $ call POST /resources '{"type":"rescue","name":"Boat 40 km","availability":1,"location":'"$(loc 40)"'}'
         $ call POST /match/$RQ
 EXPECT  first: HTTP 409 "no suitable available resource"; after adding the 40 km boat: HTTP 200, distance ~40.
 WHY     Our strategy ("the exact matching strategy is left to the students"): same type, status available,
         free capacity, within 50 km, nearest first, then most free units. Help 60 km away is too far.
 AUTO    test_matching_considers_resource_type, test_matching_considers_location

 §8  FAILURE HANDLING
=====================================================================================================================
 PDF  "Storage nodes should periodically report their availability to the coordinator using heartbeat messages."
 DO      $ cluster
         $ sleep 4; cluster
 EXPECT  6 nodes, all "ready"; the "heartbeat" column is always below ~2 s and resets every time you look.
 WHY     Every storage node sends POST /internal/nodes/heartbeat to the coordinator every 2 s.
 AUTO    test_internal_heartbeats_are_periodic

 ---- BEFORE THE FAILURE
 DO      $ for i in $(seq 1 30); do call POST /requests '{"type":"food","details":"written BEFORE the failure","auto_match":false,"location":{"lat":9.93,"lon":76.26}}' >/dev/null; [ "$(field 'd["_storage"]["shard"]')" = 1 ] && break; done; K1=$(last_id); echo "$K1 is on shard 1"
         $ field 'd["_storage"]'
         $ call GET /requests/$K1 | grep served_by
         $ cluster
 EXPECT  _storage: replicas ['storage-shard-1-0', 'storage-shard-1-1'], degraded False (BOTH copies written).
         served_by storage-shard-1-0.  cluster: both shard-1 nodes "ready" with the SAME key count.

 ---- STOP THE NODE (the PDF: "stopping the corresponding container or Kubernetes pod")
 DO      $ kubectl -n erms scale sts/storage-shard-1 --replicas=1      # stops pod storage-shard-1-1
                                                                       # Compose: docker compose stop storage-1b
         $ sleep 10

 PDF  "Detect unavailable storage nodes."
 DO      $ cluster
         $ kubectl -n erms logs deploy/coordinator --since=60s | grep "NODE DOWN"
 EXPECT  storage-shard-1-1  down  (heartbeat ~11 s ago).  Log: "NODE DOWN: storage-shard-1-1 (shard 1) - no
         heartbeat for 7.0s".
 WHY     No heartbeat for 6 s (3 missed beats) -> the coordinator marks the node down. A failed call to a node
         also marks it down immediately.

 PDF  "Use an available replica when required data remains accessible."
 DO      $ call GET /requests/$K1 | grep served_by
         $ ccall GET /health
 EXPECT  HTTP 200, served_by storage-shard-1-0.  Coordinator: healthy_shards [0, 1, 2].
 WHY     Shard 1 still has one ready copy with all the data, so reads are served from that replica; the shard
         counts as healthy.

 PDF  "Avoid routing new requests to failed nodes."  +  "Continue processing when sufficient replicas are available."
 DO      $ for i in $(seq 1 30); do call POST /requests '{"type":"food","details":"written DURING the failure","auto_match":false,"location":{"lat":9.93,"lon":76.26}}' >/dev/null; [ "$(field 'd["_storage"]["shard"]')" = 1 ] && break; done; K2=$(last_id)
         $ field 'd["_storage"]'
         $ call PUT /requests/$K1/status '{"status":"cancelled"}' | head -1
 EXPECT  the new request: HTTP 201, replicas ['storage-shard-1-0'] ONLY, degraded True.
         the status update: HTTP 200.
 WHY     The coordinator sends new writes only to live nodes - the failed node is skipped (avoid routing). One
         live copy is enough to keep working (continue processing); "degraded" honestly says the 2nd copy is
         missing and will be filled in on recovery.

 ---- RESTART THE NODE
 DO      $ kubectl -n erms scale sts/storage-shard-1 --replicas=2      # Compose: docker compose start storage-1b
         $ kubectl -n erms rollout status sts/storage-shard-1
         $ sleep 6

 PDF  "Synchronize required data when a failed node recovers."   ---- AFTER THE FAILURE
 DO      $ cluster
         $ kubectl -n erms logs storage-shard-1-1 | grep "SYNC complete" | tail -1
                                                    # Compose: docker compose logs storage-1b | grep "SYNC complete" | tail -1
         $ call GET /requests/$K2 | grep -E 'details|served_by'
 EXPECT  storage-shard-1-1 "ready" again with the SAME key count as storage-shard-1-0.
         Log: "SYNC complete from http://...: received N records, applied 2 updates; now READY".
         K2 ("written DURING the failure") is readable.
 WHY     On return the node registers, the coordinator tells it to sync, and it copies a snapshot from its ready
         partner, merging by version (newest wins). "applied 2 updates" = exactly what it missed: the new request
         K2 and the cancel of K1. It serves reads only AFTER the sync, so it never returns stale data.

 PDF  "The demonstration should show system behavior before, during, and after the failure."
 ->   the three blocks above.  Same on the pod that SERVES the reads (Kubernetes recreates it by itself):
 DO      $ kubectl -n erms delete pod storage-shard-1-0
         $ call GET /requests/$K1 | grep served_by
         $ kubectl -n erms wait --for=condition=Ready pod/storage-shard-1-0 --timeout=120s; sleep 5; cluster
 EXPECT  the read still works, now served_by storage-shard-1-1; the pod comes back (same name, same disk),
         resyncs and is "ready".
 WHY     Reads fail over to the other replica; the StatefulSet recreates the pod with its persistent volume.
 AUTO    test_storage_node_failure_before_during_after, test_k8s_storage_pod_killed_reads_fail_over_then_resync
 Grafana (optional, http://localhost:30030): during the failure the node turns RED, "Read failovers" rises;
         after the restart it turns GREEN.

         (the new pod shows 0/1 for its first ~10 s while it starts, then 1/1).
 WHY     The Deployment controller always restores the desired number of pods; the other replica serves
         meanwhile. A crashed (not deleted) container is restarted by the kubelet's liveness probe.

 §12  LEFT TO YOUR DESIGN  ("Students should be able to justify their choices.")
=====================================================================================================================
 Nothing to "pass" here: for each choice -> what we chose, how to SHOW it, and the justification.

 12.1 Programming language and web framework
      CHOICE  Python 3.12 + FastAPI (async), httpx (HTTP client), aio-pika (RabbitMQ client).
      SHOW    $ head -3 coordinator/Dockerfile;  $ cat requirements.txt;  browser: http://localhost:30080/docs
      WHY     Async I/O suits a system that mostly waits on the network (replicas, broker); FastAPI validates every
              input from typed models (automatic 422) and generates the Swagger documentation.

 12.2 Database or storage mechanism used by individual shards
      CHOICE  SQLite, one database file per storage node, on its own persistent volume.
      SHOW    $ kubectl -n erms get pvc          (one volume per storage pod)
      WHY     Durable, transactional and zero-maintenance; each node owns its data; every write is flushed to disk
              (synchronous=FULL) before it is acknowledged.

 12.3 Exact sharding and partitioning strategy
      CHOICE  shard = sha256(key) mod 3; keys "request:<id>" and "resource:<type>:<id>".
      SHOW    §10.4 (hand-computed hash = the coordinator's choice).
      WHY     A stable hash (Python's own hash() differs per process) so every service agrees; random ids spread
              evenly; the type inside resource keys lets matching scan only resources of the needed type.

 12.4 Replica synchronization mechanism
      CHOICE  The coordinator writes to ALL live replicas in parallel; each record has a version; on recovery a
              node copies a snapshot (incl. deletes) from a ready replica and merges it - newest version wins.
      SHOW    §8 AFTER ("applied 2 updates").
      WHY     Version-based merging is idempotent and order-independent; only missed updates are applied; a node
              serves reads only after it is synchronized. Each sync order carries an id and is re-sent if lost.

 12.5 Resource-matching strategy
      CHOICE  same type + status available + free units + within 50 km (haversine); nearest first, then most
              free units; the unit is claimed with compare-and-set before the request is marked matched.
      SHOW    §7 "MATCHING CONSIDERS ..." and §11.4.
      WHY     Nearest help arrives first; compare-and-set prevents two matchers from giving away the same unit.

 12.6 RabbitMQ exchange, queue, and routing configuration
      CHOICE  topic exchange erms.requests -> durable queue matching.requests (routing key request.#),
              persistent messages, manual acknowledgement, prefetch 2 per worker. Retry: exchange erms.retry ->
              queue matching.retry (5 s TTL) -> back to erms.requests; after 12 attempts "unmatched".
      SHOW    §11.5 bindings; RabbitMQ UI -> Exchanges / Queues.
      WHY     Durable + persistent + ack-after-work = no message loss; competing consumers share the load; the
              delayed retry queue retries without blocking a worker.

 12.7 Microservice boundaries and internal API design
      CHOICE  request-service (client REST API), matching-service (RabbitMQ consumer + matching), coordinator
              (routing, replication, failure detection) + storage nodes. Internal API: register, heartbeat,
              PUT / GET / DELETE /internal/data/{key}, as in PDF §6.
      SHOW    $ kubectl -n erms get deploy,sts;  http://localhost:30081/docs (coordinator API)
      WHY     Stateless parts scale independently of the stateful storage tier; each service has one job.

 12.8 Kubernetes deployment configuration
      CHOICE  Deployments for stateless services, StatefulSets + persistent volumes for storage and RabbitMQ,
              Services + NodePorts, readiness / liveness probes, passwords in Secrets, resource limits.
      SHOW    $ ls k8s/;  $ kubectl -n erms get deploy,sts,svc,pvc,secrets
      WHY     Stable identity + disk where state lives; self-healing via probes; no passwords in files.

 12.9 Monitoring and logging approach
      CHOICE  Every service exposes /metrics; Prometheus scrapes them, Grafana shows the "ERMS overview"
              dashboard; structured logs per service (NODE DOWN, SYNC complete, MATCHED ...); /cluster view.
      SHOW    Grafana http://localhost:30030;  $ kubectl -n erms logs deploy/coordinator | tail
      WHY     Failures and recovery are visible live (red / green, failovers, resync duration, queue depth).

 12.10 Optional cloud platform and deployment architecture
      CHOICE  Not used (optional): deployed locally on Minikube, as the PDF allows.
      WHY     The same manifests (k8s/*.yaml) would run on a cloud Kubernetes cluster without code changes.
